# V6.4 Evidence Report Generation

## 1. 背景与范围

V6.4 将已完成 Research Task 的结果整理为可预览、审批、保存及回滚的研究报告。生成器不重新回答问题，不调用 LLM、Retriever、Web Provider 或 Evidence Factory。网页来源始终作为数据，不拥有写入权限。

本阶段没有前端报告页面、在线编辑器、自动发布、新版 Evidence Schema 或第二套版本/审批系统。

## 2. Report 模型与存储

`EvidenceReport` 包含 report_id、task_id、title、summary、task_description、sections、conclusions、evidence_refs、warnings、quality、status、created_at 和 exports。

- summary 保留已保存研究正文。
- conclusions 保存逐结论文本和原始 Evidence ID 列表。
- evidence_refs 是已有 Unified Evidence 4.0 的复制，不分配新 ID。
- exports 将 md/docx 分别关联到既有 file_id 和 action_id。
- DRAFT、PENDING_APPROVAL、EXPORTED 是报告展示状态，由关联审批记录派生，不是新的 Research 状态机。

草稿存放在现有 Research checkpoint 的 `result.reports[report_id]`。保存时使用 SQLite 写锁合并报告，保留原结果、其他草稿和不同格式的导出关联。不新增数据库表、迁移或 Evidence Schema。

## 3. 数据流

```text
已完成的 Research Task
  → 保存的 answer + unified_evidence + web_search_warnings
  → 现有 evaluate_evidence_quality
  → 确定性 Report Draft
  → Markdown 文本预览
  → 原 Diff / 冻结目标、正文、expected_hash
  → 原 pending_actions / Human Approval
  → 原版本化写入事务
       ├─ .docx：原 write_word
       └─ .md：同一事务中的 UTF-8 格式适配
  → 原 Version 快照、历史列表与经审批的 Rollback
```

草稿及预览只保存数据库记录，不创建报告文件。首次预览分配 `report-<report_id>.md` 或 `.docx` 的文件登记作为审批目标；未审批目标不存在，无法通过下载 API 导出。

报告包含标题、任务说明、摘要、分析过程、核心结论、Evidence 来源及限制说明。分析过程只描述本生成器实际执行的整理和检查步骤，不虚构研究过程或披露模型隐式推理。

## 4. Evidence 引用与 Quality Gate

生成前重新调用 V6.2 Quality Gate，输入保存的研究正文和 Unified Evidence，不信任客户端提供的新结论或证据。使用 Gate 的逐片段关联结果生成 `conclusions[].evidence_refs`；无法关联的结论保留正文和空引用列表，并明确显示“未建立证据关联”。

报告来源列表包含原 Evidence ID、本地文件名及页/行/Chunk/Block/表格/Markdown heading_path 等定位；Web 来源保留 URL 与 retrieved_at。

Quality warnings 和 V6.3 web_search_warnings 一并保存和导出。WARNING 允许生成草稿，不证明结论错误；PASS 也不证明事实正确。已有视觉高影响写入保护仍在审批前执行，不因报告功能放宽。

## 5. Markdown 与 Word 导出

两种格式使用同一份冻结报告正文。外部文本的 HTML 和 Markdown 特殊字符按字面内容转义，避免来源内容成为报告结构或自动加载图片的指令。

- Markdown：UTF-8 `.md`，保留标题、结论、来源及 warnings。
- Word：复用原 `write_word` 原子写入逻辑。确认后才创建空 DOCX，再由原 Writer 追加报告正文；标题和章节以正文文本呈现，本阶段不提供 Word 样式/目录排版。
- 文件名由系统生成，API 不接受任意磁盘路径、文件内容、Evidence 或自定义导出目标。
- 导出的文件登记为不可检索，未自动建立索引；本阶段不额外触发 Document Pipeline。

## 6. Approval、Diff 与 Version

现有 `confirmation.py` 增加 `write_report` 类型和报告适配入口，继续复用 `_create_pending_word_action`、`confirm_action`、`cancel_action`、审批绑定校验及数据库原子领取。未新增 Tool 注册或修改 Tool Boundary。

现有 `file_versioning.py` 增加受限的报告路径和格式适配，保留同一套 preview、expected_hash、快照、版本事务、失败补偿及回滚逻辑。

- 新文件预览冻结 `expected_hash=ABSENT`；确认时若目标已出现，拒绝覆盖。
- 既有文件沿用内容 hash 检查；操作/目标绑定被篡改时拒绝执行。
- 取消审批不写报告文件、不产生文件版本；重复确认不会再次执行。
- Word 和 Markdown 快照继续使用现有版本表、parent_version_id 和哈希校验。
- 首次写入记录空文档基线及写入后的版本。回滚到首个基线恢复空文档，而非删除文件；回滚操作自身也新增版本。
- 新文件写入或版本事务失败时删除本次创建的报告文件和快照；已有文件沿用恢复原字节的补偿行为。
- 同一草稿、同一格式的重复预览复用 pending/confirmed/executed action；取消或失败后允许重新预览。

## 7. API

| 方法与路径 | 作用 |
| --- | --- |
| POST `/api/research-task/{task_id}/reports` | 从已完成任务生成草稿；body 为 `{"title":"证据研究报告"}` |
| GET `/api/research-task/{task_id}/reports/{report_id}` | 获取草稿、引用、警告及各格式审批状态 |
| POST `/api/research-task/{task_id}/reports/{report_id}/preview` | body 为 `{"format":"md"}` 或 `{"format":"docx"}`；返回原审批对象和 Diff |
| GET `/api/research-task/{task_id}/reports/{report_id}/download?format=md` | 仅在对应审批已执行且文件存在时返回当前文件 |

实际确认/拒绝使用项目已有 Action API，不新增另一套确认端点。历史版本和回滚继续使用 `/api/files/{file_id}/versions` 及已有 rollback/confirm 接口。Report ID 必须属于指定 Task。

下载的是文件当前状态，回滚后下载到回滚内容；报告 EXPORTED 表示曾成功导出，不保证文件仍是最初导出的版本。接口沿用项目既有身份与会话体系，不新增认证机制。

## 10. 限制

- 单任务最多 20 份报告，研究正文最多 80,000 字符，渲染正文受既有 100,000 字符审批限制，Research checkpoint 保持 8 MiB 上限。超限明确返回错误，不静默截断正文。
- 覆盖关系继承 V6.2 规则与上限，不做语义蕴含或事实真假判断；超出关联检查范围的结论保留为空引用并显示警告。
- 报告草稿不可在线编辑，修改标题/内容需求通过新的研究结果或新草稿处理。
- 预览或取消后可能保留未落盘的目标登记记录，以便重新预览；这不是已生成的文件，也不产生版本。
- 采用现有 Word Writer 的正文格式，不提供精细排版、自动目录或报告网页预览。
- 沿用原版本事务的并发/崩溃恢复边界，不新增跨进程文件锁或分布式事务。
- 不自动确认、不创建 tag、不进入 V6 Final Freeze；提交后等待人工验收。
