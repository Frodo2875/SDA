# 聊天文档操作与用户确认

三种聊天模式共用“文档操作”入口，模式决定回答执行方式，不决定用户能否保存文档。

## 操作流程

1. 普通回答或研究完成后，选择回答并编辑待保存正文。
2. 新建 Word / Markdown，或者选择已有可写 Word，将正文追加到末尾。
3. 点击“预览保存”，查看目标文件及修改前后内容。
4. 点击确认后执行并生成版本；取消不修改目标文件。

删除、撤销、恢复历史版本复用已有 API，同样先生成操作确认卡片。
参考资料默认隐藏不影响操作确认卡片的展示。
回答下方的证据质量提示和详细处理记录也默认隐藏，可在“显示选项”中主动开启；错误与操作确认不会被隐藏。
产品 Logo 显示在左上角，并同时作为浏览器页面图标。
聊天模式选择器位于输入框左侧；模式仍为普通问答、深度研究和报告生成，执行逻辑不变。
聊天页的“新建聊天、最近聊天、文档操作、显示选项”采用 2×2 紧凑布局，展开内容仍保留足够宽度。

## 实现

- `frontend/components/document_actions.py`：三种模式的统一交互。
- `backend/document_action_api.py`：仅接收用户发起的草稿预览请求。
- `POST /api/document-actions/preview`：校验当前会话的已完成回答，读取服务器保存的来源信息，复用 `create_pending_report_action`。
- 同步回答从聊天记录读取；研究结果从当前会话的已完成 Research Task 读取。
- `backend/agent.py`：纠正“没有写入权限”的旧提示，说明草稿、预览和确认操作。
- `backend/services/document_capabilities.py`：对独立的 Word 编辑能力询问直接返回系统功能说明，避免模型把未暴露直接执行工具误解为没有文档保存能力。实际编辑指令仍进入原执行流程。
- 实际写入继续使用原有 Approval、Diff、Version 和文件权限检查；模型不能自行调用确认接口。

## 边界

本次提供正文草稿编辑、新文件保存、Word 追加以及已有文件管理操作。
没有增加任意代码执行、Excel/PDF 原文编辑、Word 原文覆盖或系统只读文件写入权限。
新文档沿用报告文件名与存储约束；预览会登记文件目标，但确认前不会写入文件内容或版本。
保存不代表自动关联当前知识库，也不代表已经完成解析和索引。
识别冲突及低置信度检查继续生效；来源信息由服务器读取，前端不能通过省略资料信息绕过检查。
模型或文档中的 `confirmed=true` 不是用户确认。
系统直接生成的功能说明不执行资料质量检查；普通问答和研究分析继续执行原有检查。
代码更新后需重启后端并重新提问，已经保存的旧回答不会自动改写。

## 验证

`tests/test_chat_document_actions.py` 覆盖三种模式入口、草稿编辑、确认/取消、新建与追加、只读目标、预览后文件变化、来源归属、识别风险、非法参数，以及删除/撤销/恢复入口。

2026-09-16 最终验证：全量 `pytest -q` 为 818 passed，耗时 91.85 秒。
其中 Word 能力说明与文档操作定向测试为 35 passed，耗时 5.74 秒。
测试使用隔离数据库和文件目录；页面交互使用 Streamlit AppTest，外部模型响应为测试替身。
