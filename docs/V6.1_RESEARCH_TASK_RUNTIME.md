# V6.1 Research Task Runtime

## 1. 设计背景与开发基线

分支：`feature/v6-development`。开发基线：`7200a98`（V6.0 Markdown 正式支持）。
V5/V6.0 已有文档处理、本地/Web/跨源检索和 Unified Evidence 4.0。
本阶段增加用户级 Research Task 封装，不替代既有 Agent、Workflow 或 Async Runtime。

## 2. 为什么需要 Research Task

复杂研究涉及多次模型/工具调用，不能让用户只等待一次同步 HTTP 响应。
Research Task 将创建、后台执行、状态查询、取消、重试/恢复和结果读取分开，
让已完成的读取结果与原任务身份能够持久化保留。
本阶段不新增报告 Writer 或 Evidence Quality Gate，“生成报告”只触发复杂任务调度，
其内容生成和审批能力仍受既有 Agent 能力限制。

## 3. 编码前架构扫描结论

| 现有模块 | 已有能力 | 缺失能力 / 本轮扩展 |
| --- | --- | --- |
| `runtime/async_task_runtime.py` | 持久化队列、原子领取、文档/Batch/Workflow handler、取消、Retry/Resume | 新增 research handler；沿用原状态及任务表 |
| `runtime/task_runner.py` / `planner.py` | TaskPlan、步骤、条件、审批、节点 checkpoint | 允许在同一创建事务初始化 Async metadata；Research 不复制执行器 |
| `repositories/task_repository.py` | SQLite tasks/task_steps、事务领取 | 在创建事务中实现 5 分钟去重；原子合并 checkpoint/取消标记及研究重试状态 |
| `agent.py` | 唯一 Tool Calling 循环、Source/Tool 边界、Evidence 收集 | 可选 observer：真实阶段、模型次数、已完成/待执行调用和恢复；默认同步路径不启用 |
| 默认异步 workflow handler | 调用 `run_agent` 后绑定子任务 | Research 在 Agent 初始化时保存原 Workflow ID；恢复不创建新子 Workflow |
| `services/trace_service.py` | 事件、状态、时长、Token、脱敏 | 直接复用，新增 research_request/research_stage 事件，不修改 Trace 实现 |
| `main.py` | 同步 Chat、通用 Async API、BackgroundTasks | 确定性复杂度分流和 Research API；Research 使用既有线程桥接，避免同步工具占用 HTTP 事件循环 |

扫描先于代码修改完成。实现没有引入 Celery、Redis、Kafka、外部队列、额外数据库表或 migration。

## 4. 整体架构

```text
POST /api/chat
 -> Task Complexity Router（确定性规则）
    -> 简单：既有 run_agent -> 同步 ChatResponse
    -> 复杂：ResearchTaskRequest -> enqueue_async_task(task_type=research)
                                   -> TaskPlan + tasks/task_steps + checkpoint
                                   -> 返回 task_id

POST /research-task（显式请求异步，不需要满足复杂度规则）
 -> 同一 enqueue_async_task

FastAPI BackgroundTasks
 -> dispatch_research_task
 -> 既有 Async Runtime 的 _run_sync_handler 线程桥接
 -> run_async_task（同一事务领取 / 状态 / handler / finalize）
 -> execute_research -> 既有 run_agent + 可选 ResearchObserver
 -> 原 Source Router / Tool Boundary / Retrieval / Workflow / Evidence
 -> checkpoint 保存结果 -> 原 Async finalize
 -> GET /research-task/{task_id}
```

ResearchObserver 只观察和保存，不执行工具。同步工具在后台工作线程中的 Agent 事件循环运行，
HTTP 事件循环仍可处理轮询和取消。通用 `/api/tasks` API 调度 research 时也走同一桥接。

### 复杂度规则

`route_task_complexity` 使用既有 `route_source` 的结果作为只读信号，不修改来源策略。
以下任一条件触发异步：

- 明确生成/撰写/编写/制作/输出报告（含有限英文表达）；
- 批量/所有材料，或十份以上文档的数量提示；
- BOTH 来源；
- 预测调用数达到 4，或长查询同时包含多个分析操作。

预测值是固定规则：基础 1 + 分析操作词数 + BOTH 的 2 + 批量的 3。
这只是调度提示，不是实际调用承诺或授权。单次网页查询、天气、简单本地读取继续同步。
显式 `/research-task` 可用于绕过启发式的漏判；本轮没有 LLM 自由决定调度模式。

## 5. 状态与进度设计

不新增状态存储。下列用户状态从原 Async `task_status` 和 `progress_detail.stage` 派生：

| 用户状态 | 底层状态 / 条件 |
| --- | --- |
| CREATED | created |
| RUNNING | running，且不处于工具调用阶段 |
| WAITING_TOOL | running + LOCAL_RETRIEVAL / WEB_RETRIEVAL / WAITING_TOOL 阶段 |
| COMPLETED | success |
| FAILED | failed |
| CANCELLED | cancelled |
| WAITING_CONFIRMATION | 沿用 waiting_confirmation，不能错报为已完成 |
| PAUSED / PARTIAL_SUCCESS | 兼容原 Async 状态，未建立另一套状态机 |

阶段包括 CREATED、PLANNING、LOCAL_RETRIEVAL、WEB_RETRIEVAL、EVIDENCE_CHECK、GENERATING、COMPLETED。
通用工具使用 WAITING_TOOL 阶段。阶段按实际调用更新，可以多次出现，不伪造未发生的 Web/本地检索。
EVIDENCE_CHECK 表示原 Agent 的最终回答/必要工具检查，不是 V6.2 Quality Gate。
运行中 `progress.percent=null`，完成后为 100；不根据模型轮数虚构完成百分比。

研究状态 Trace 关联外层任务；没有子 Workflow 的模型/工具 Trace 也关联外层 ID。
已有子 Workflow 的步骤与 Trace 保留在原子任务下，可由 checkpoint 的 child ID 追溯。
审批等待沿用原动作接口，取消审批通过原 `/api/actions/{action_id}/cancel`，不绕过 Approval。

## 6. API 设计

主路径及 `/api` 前缀别名具有相同行为：

| 方法 | 路径 | 行为 |
| --- | --- | --- |
| POST | `/research-task` | 显式创建/复用研究任务，202；保存后后台执行 |
| GET | `/research-task/{task_id}` | 返回状态、阶段、时间、结果、错误与重试次数 |
| POST | `/research-task/{task_id}/cancel` | 原取消机制；运行中登记协作式取消 |
| POST | `/research-task/{task_id}/retry` | 原 Retry，最多 2 次；Research 保留执行 checkpoint |
| POST | `/research-task/{task_id}/resume` | 原 Resume；恢复失败/取消/暂停任务的 checkpoint |

请求示例：

```json
{"session_id":"research-session-1","query":"分析100份学生材料，结合网页总结规律并生成报告"}
```

响应主要字段：`id/task_id`、`session_id`、`status`、`query`、`created_at`、`updated_at`、
`progress`、`result`、`error`、`cancel_requested`、`retry_count`。
首次创建返回 CREATED，重复提交返回已存在任务的当前状态。
成功结果保存 answer/status、Evidence、Unified Evidence、子 Workflow ID 和可能的 pending_action；
运行中/失败/取消时不将不完整结果当作正式结果返回。
未知 ID 返回 404，状态不允许操作返回 409，无效创建参数返回 422。

Chat 保持原响应结构：复杂请求返回 `status=research_task_created`、task_id、空 tool_calls 和说明；
简单请求仍返回原同步答案。没有新增前端界面。

## 7. 执行、去重与恢复

### 创建和去重

Research Task 使用 `async_research` TaskPlan 和一个既有 Async 执行步骤。
初始 created 状态、payload、checkpoint 与步骤在同一 SQLite 事务中保存。
`BEGIN IMMEDIATE` 内查询同 session、同 query SHA-256、最近 300 秒的任务，再决定是否插入。
不同会话或不同查询不合并；查询仅去首尾空白，保留内部空白和大小写，避免合并语义不同的代码/资料。
失败、取消和完成的任务在窗口内同样复用，用户通过 Retry/Resume 明确继续。
多个后台调度同时到达时，原 `claim_async` 只允许一个 worker 领取。

### Checkpoint

使用原 `checkpoint_data.async_task.checkpoint` JSON，保存：

- 初次解析后的消息上下文、Domain/Source route 及原 Workflow ID；
- Agent 消息协议、已完成工具结果、剩余待执行工具调用；
- tool_rounds、llm_attempts、必要工具补问次数；
- 最终可读取结果。

模型请求前保存尝试计数，工具完成后保存其结果和待执行调用列表。
恢复继续原 Agent 循环，不复制调用逻辑，不再次执行已持久化的成功工具；
剩余工具仍走原参数/来源/安全检查。恢复不重置模型/工具轮次上限。
Research Retry 保留 checkpoint，其他任务的 Retry 行为保持不变。
研究重排队在事务内检查原 updated_at 和终态，避免并发 Retry/Resume 把正在运行的任务重新排队。

Checkpoint 更新与取消标记使用同一事务合并，避免刚完成的工具结果覆盖取消请求。
取消在模型/工具调用间检查，当前同步调用不能被安全强杀；先保存已完成结果再停止。
有待确认动作时继续使用原审批绑定和同步机制；恢复已取消/失败的审批结果返回明确错误，
不能重新生成写入动作。已执行动作不会重复写入。

## 8. 异常处理

- 抛出的异常由原 Async Runtime 转成 `ASYNC_TASK_EXECUTION_ERROR` 和固定安全消息，不把异常文本/API Key 放入任务错误或 Trace。
- 非完成 Agent 状态不能算成功；预算耗尽映射 `RESEARCH_BUDGET_EXHAUSTED`，缺少必要调用映射 `RESEARCH_INCOMPLETE`，其他错误映射 `RESEARCH_AGENT_FAILED`。
- 成功结果通过现有 redaction 处理；错误响应不暴露原始 traceback。
- Checkpoint 最大 8 MiB，超限明确失败，不无限增长内存/数据库数据。
- 已完成任务不能重新领取；运行中的任务不能直接 Resume，防止双重执行。
- 失败的读取仍保留原 Tool 有界重试规则，Research 不新增 Web 重试逻辑。

## 11. 限制与下一阶段

- BackgroundTasks 和本地线程不是分布式队列；进程强制退出后不会自动接管 running 任务。已经保存的 checkpoint 可用于后续受控恢复设计，但本轮不承诺崩溃后自动恢复。
- 已完成调用返回与 checkpoint 提交之间仍有进程崩溃窗口，不宣称所有操作 exactly-once；写入继续依赖原 Approval/Version 防重放。
- 恢复使用已保存的研究上下文/工具结果，不自动检测所有来源文件原地修改或网页变化。资料更新后需要新任务，不把旧证据当成新抓取结果。
- 原 Agent 的调用上限仍有效；复杂度判断不意味着一次运行一定能处理 100 份资料或生成完整正式报告。
- 5 分钟以外相同查询可新建任务；session_id 沿用现有项目会话语义，不是新引入的认证系统。
- 尚无跨任务并发额度、自动清理或长期归档；checkpoint 有容量上限。
- 本阶段只提供后端 API/Trace，不新增 V7 前端。
- V6.2 可在现有任务/结果/证据边界接入 Quality Gate；本轮没有实现 Gate，也没有改 Evidence Schema。
- 通过全量回归后提交 `V6.1 research task runtime`，不创建 tag，等待人工验收。
