# V6.3 Web Search Reliability

## 1. 背景与现状审计

V6.1 管理研究任务执行，V6.2 检查交付证据。V6.3 仅增强现有 Tavily 搜索的请求可靠性，不增加搜索能力、Provider Router、多 Provider 切换或消息队列。

开发前扫描结果：

- 请求：`retrieve_web → WebRetrievalService → SearchProvider.search`；Factory 根据环境创建 Tavily，未配置时返回 UnavailableSearchProvider。
- Tavily 使用同步 httpx POST，已有明确 timeout、401/403/429 和部分网络异常映射，但不读取 Retry-After、不重试。
- 结果：Tavily 检查 JSON/results 后转换条目，再进入 `normalize_search_results` 的 URL/安全处理及现有 UnifiedEvidenceFactory。
- 缺口：条目字段未充分验证，异常 metadata 可能触发非预期异常；没有任务内重复查询复用；Trace 缺少独立 Provider 请求观测。
- 原有测试明确要求 `WEB_SEARCH_*` 错误码及空结果 `ok=true/status=not_found`。这些契约必须保留。

## 2. 架构与修改文件

```text
retrieve_web
  → WebRetrievalService
  → reliable_search（当前 Research 执行范围内查重）
  → Tavily.search
      → HTTP 请求 / 429 有界重试
      → JSON、results、条目字段校验
  → normalize_search_results（原安全处理）
  → 原 UnifiedEvidenceFactory / Unified Evidence 4.0
  → 原 Retrieval 响应 + provider_execution / search_error_code
```

Reliability Layer 是现有单 Provider 调用的包装，不注册新 Provider。Direct URL Fetch 分支保持不变。

| 文件 | 改动 |
| --- | --- |
| backend/services/search_reliability.py | 新增执行范围、结果复用、错误分类、Provider Trace |
| backend/services/search_provider.py | SearchProviderError 增加稳定分类属性和执行信息；未配置错误使用固定提示 |
| backend/services/tavily_search_provider.py | 429 有界重试、Retry-After、字段校验、网络错误分类 |
| backend/services/web_retrieval.py | 搜索分支挂接 Reliability Layer，附加观测及分类字段 |

| backend/services/research_task.py | Agent 调用外围建立搜索作用域，保存 Web 降级信息 |
| tests/test_web_search_reliability_v63.py | 新增离线契约及真实 Research/Agent 集成测试 |
| docs/V6.3_WEB_SEARCH_RELIABILITY.md | 本文档 |

不修改旧测试或增加依赖。Source Router、Tool Boundary、Cross Source Retrieval、UnifiedEvidenceFactory、Evidence Schema、Evidence Quality Gate、Async/Workflow Runtime 核心均保留原实现。

## 3. 错误码与兼容策略

V6.3 稳定分类保存在 `SearchProviderError.search_error_code`、响应 `data.search_error_code` 和 `data.provider_execution.error_code`。Provider Trace 的 error_code 使用同一分类。原响应顶层 error_code 和异常 error_code 继续使用旧契约，避免破坏 V5 调用方。

| V6.3 分类 | 条件 | 旧兼容错误码 |
| --- | --- | --- |
| SEARCH_PROVIDER_UNAVAILABLE | 未配置、配置错误、HTTP 非成功状态或其他 Provider 故障 | WEB_SEARCH_PROVIDER_ERROR |
| SEARCH_AUTH_FAILED | HTTP 401 / 403 | WEB_SEARCH_AUTH_ERROR |
| SEARCH_RATE_LIMIT | HTTP 429，重试后仍受限或等待超预算 | WEB_SEARCH_RATE_LIMITED |
| SEARCH_TIMEOUT | httpx 超时或兼容接口 TimeoutError | WEB_SEARCH_TIMEOUT |
| SEARCH_NETWORK_ERROR | httpx 连接/传输异常或兼容接口 OSError | WEB_SEARCH_PROVIDER_ERROR |
| SEARCH_INVALID_RESPONSE | JSON/results/条目/规范化格式无效 | WEB_SEARCH_INVALID_RESPONSE；兼容规范化异常可能保留 WEB_SEARCH_PROVIDER_ERROR |
| SEARCH_EMPTY_RESULT | results 为空 | 保持成功的 not_found，顶层 error_code 为 null |

错误消息使用固定文本，不将 Provider body、Header、API Key、原始异常或堆栈传入用户响应。网络错误由程序分类，不交给 LLM 判断。原有输入参数校验仍在既有入口执行。

## 4. Retry 与 Timeout

- 只对 HTTP 429 自动重试，最多一次；单次 search 最多发出两次 HTTP 请求。
- Retry-After 支持数值秒和 HTTP-date；过去时间按 0 秒处理。
- 缺失、无法解析或非有限值使用 1 秒默认等待。
- 最大等待预算为 2 秒。有效 Retry-After 大于 2 秒时直接返回 SEARCH_RATE_LIMIT，不缩短服务器要求的等待后提前重试。
- 第二次请求无论返回何种结果都不继续重试。401/403、其他 HTTP 故障、超时、网络异常、非法响应不自动重试。
- 沿用显式 `WEB_SEARCH_TIMEOUT_SECONDS`，默认 8 秒，配置限制为 1–30 秒；适用于 httpx 超时阶段，不宣称它是整个 Research 的硬性总时限。
- 既有 Tool Retry 不将这些 Web 错误列为可重试错误，因此不叠加外层自动重试；没有修改 Tool Boundary 或 Retry Policy。

## 5. 返回校验与任务内复用

Tavily 返回必须为 JSON 对象且 results 为列表。每个条目必须为对象，title、url 必须为非空字符串；title/url/content 长度与现有 WebSearchResult 契约一致。content 如提供必须为字符串，score 如提供必须为有限数值且不是布尔值，published_date/favicon 如提供必须为字符串。URL 必须有 HTTP(S) 主机名、合法端口且无内嵌凭证。校验失败不会进入 normalize_search_results。

正常条目继续经过原 URL 规范化、Web Safety 和 Evidence Factory，不替代任何安全边界。无 snippet 的链接仍只是搜索候选，不伪造 Evidence。

`research_search_scope` 使用 ContextVar 包围一次 Research Agent 执行。缓存键包含 Provider 实例、首尾去空白的 query、top_k、language、region；不做大小写或语义合并。成功、空结果、失败均可复用，避免同一执行重复触发限流或认证失败。

缓存最多保留 128 个不同键，超出后新键正常执行但不加入缓存。缓存读写使用深复制，避免后续结果变更污染其他调用。复用结果保留最初 retrieved_at，不伪装成新的抓取时间。

作用域在完成、异常、取消后释放，不跨 Task、用户或普通同步请求共享。没有长期缓存和新数据库表。Retry/Resume 启动新执行作用域；既有 Agent checkpoint 继续复用已经完成的 Tool 步骤，本层不单独持久化缓存。

## 6. Trace

每次搜索调用记录 `web_search_provider`，复用命中也有独立观测：

```json
{
  "provider": "tavily",
  "latency_ms": 125,
  "status": "failed",
  "error_code": "SEARCH_RATE_LIMIT",
  "attempt_count": 2,
  "retry_count": 1,
  "cache_hit": false,
  "retrieved_at": "2026-09-15T08:00:00+00:00"
}
```

status 为 success、empty 或 failed。缓存命中 attempt_count/retry_count 均为 0，表示该调用没有发出新 HTTP 请求。latency_ms 包含当前调用内的等待与校验时间，缓存命中记录为 0。

新增 Provider 事件不记录 query、结果正文、URL、Header 或 API Key。Research 事件关联当前 task_id/session_id；独立搜索记录到 `web-search` 会话，既有工具事件仍由 Agent 关联原会话。Tavily/未配置 Provider 的工具 Trace 使用 `[omitted]` 替代 query 和 search_query；旧自定义测试 Provider 的 Trace 继续使用原脱敏规则。

Trace 持久化失败不将原本可用的搜索结果变为失败；这意味着数据库异常期间可能缺少观测，不保证审计日志必达。

## 7. Research 集成

复用现有阶段：Agent 在调用 Web 工具前设置 WEB_RETRIEVAL，查询 API 映射为 WAITING_TOOL。Provider 失败由 Reliability Layer 收集固定的 WEB_SEARCH_FAILED 降级信息，结果字段 `web_search_warnings` 保存稳定分类及提示。

本阶段选择继续降级：如果 Agent 正常结束，Task 可以 COMPLETED，同时携带 Web 失败警告及 V6.2 质量结果；不把网络错误转换成虚构成功 Evidence。不要求 LLM 识别异常才能保存警告。Agent 自身未完成时仍走原 FAILED 路径，具体搜索故障可从 Provider Trace 查询。

不新增任务状态，不改变取消、重试、恢复、Checkpoint 或审批语义。

所有请求使用 httpx.MockTransport，不访问 Tavily 或消耗 API 额度。Retry 测试注入等待替身，验证实际等待参数和 HTTP 次数。

## 9. 限制与验收范围

- 没有多 Provider、自动切换、长期缓存、后台补搜或 LLM 网络错误判断。
- HTTP 超时是 httpx 阶段超时；同步搜索与最多 2 秒等待发生在现有工作线程/执行路径中，不能在 HTTP 请求中途强制取消。
- 任务复用只覆盖当前执行作用域；进程重启后依赖现有 Agent checkpoint，不恢复内存缓存。当前工具执行为顺序调用，没有增加跨线程 single-flight 协调。
- 空结果保留 V5 的 not_found 行为；调用者需读取新增分类，不能只看顶层 error_code 判断空结果。
- Web 降级不保证最终文本语义正确，证据缺口仍由现有 V6.2 Quality Gate 提示。
- 本阶段不创建 tag，不进入 V6.4，提交后等待人工验收。
